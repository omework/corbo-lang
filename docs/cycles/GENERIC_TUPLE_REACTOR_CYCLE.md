# Generic identities, caller result graphs and network registrations

Date: 2026-11-18. Scope: corboc compiler/runtime mechanisms and directly related
regressions. The Rust bootstrap was not modified. No normative language rule or
public STD API changed. No independent adversarial audit or mutation campaign was
performed in this cycle.

## Implemented mechanisms

1. Concrete nominal types are interned by template and the complete concrete
   argument list, including nested instance identities. Dependency substitutions
   distinguish source occurrences within an outer specialization. Constructor,
   projection and structural-contract inference use those identities. Numeric
   constructor fields retain their declared context; untyped locals do not stop
   the search for an enum constructor's enclosing result context.
2. Borrow-bearing tuple returns instantiate immutable caller-owned value graphs.
   Tuple positions, record fields, formal-to-actual environments and symbolic
   external roots are represented separately from mutable callee field nodes.
   Successive calls, tuple moves, destructuring, relay calls and task captures
   preserve their own roots. Inline field borrows retain containing storage;
   references already stored in a field forward their external target. Record
   payload identity checks use the nominal declaration instead of a variant's
   spelling. Dependency-free owned task arguments do not create an external
   lifetime obligation. Nested match receivers and void returns retain their
   enclosing destination.
3. Unix readiness uses descriptor cohorts with monotonically increasing tokens,
   aggregate read/write interests and intrusive waiter lists. Dispatch detaches
   registrations before wakeup, rearms remaining interests, ignores stale cohorts
   and propagates registration/rearm errors. Linux uses epoll ADD/MOD and Darwin
   uses separate kqueue filters. Windows uses independent OVERLAPPED requests,
   authenticated STD hooks, IOCP dequeue and a park/wake handshake. Each request
   remains live until dequeue, including synchronous submission success.

The readable runtime fragments are in `runtime/async/`. The resource bridge was
regenerated; native queue/completion operations remain target-selected `@asm` in
`stdlib/src/sys/net/reactor/`.

## Reproduction

Use a seed supporting the active grammar, then run:

```sh
corboc --emit-package-c compiler/corboc --stdlib-dir stdlib/src > /tmp/corboc.c
cc -std=c11 -pthread -O1 /tmp/corboc.c -lm -o /tmp/corboc
python3 validation/check_core_mechanisms.py --corboc /tmp/corboc --keep /tmp/mechanisms
python3 validation/check_network_waits.py --corboc /tmp/corboc --keep /tmp/network --registry unix
python3 validation/check_generic_structs.py --native-only --corboc /tmp/corboc
python3 validation/check_core_extensions.py --corboc /tmp/corboc --keep /tmp/core-extensions
python3 validation/check_std_iter.py --corboc /tmp/corboc
```

`validation/create_target_emitter.py` creates a **test-only host-running emitter**
for a selected target. It changes target-query/assembly-selection helper bodies
in a temporary compiler copy, keeping host I/O so the emitter runs locally. Its
output is then compiled and executed by the target C compiler/runner. This does
not establish that a complete native compiler binary runs on those other OSes.
The normal compiler has no new cross-compilation CLI option.

Both execution scripts accept `--cc` and `--runner`. The mechanism script accepts
`--reuse-c` for portable generated programs; network code must be generated by
the corresponding target emitter. Use `--registry windows` for the IOCP witness.
Local sockets, Docker and Wine need the applicable host permissions.

Retained artifacts for this run are under `/tmp/corbo-three-mechanisms/`;
Linux artifacts are under `/private/tmp/corbo-iter-std/core-mechanisms/`.

## Limits and discrepancies

- Windows execution used Wine, not native Windows. Windows ARM64 remains
  explicitly deferred by the user. These results do not close that platform gap.
- Host ASan execution of the deterministic registry witness stalled without a
  result and was terminated. It is **inconclusive**; the completed UBSan runs
  above are the sanitizer evidence for this cycle.
- Summary storage is bounded. Arena exhaustion and unsupported summary forms are
  rejected conservatively. Arbitrary conditional borrow-bearing tuple contracts
  and every possible nested payload shape were not established by this suite.
- Additional enum probing exposed a pre-existing conservative refusal of borrowed
  scalar payload consumption in the following standalone form (also refused by
  the previous seed): `enum E { No, Yes { value: i64 } }`, construct `E.Yes`, then
  `match &e { E.Yes { value: value } => { print(*value); }, E.No => {} }`.
  Borrowed projections of enum payloads are not claimed by the nested-enum layout
  witness, which constructs, moves and destroys distinct enum specializations.
- Runtime threads/queues are process-lifetime infrastructure. No cancellation,
  custom runtime interface or new shutdown API was introduced.
